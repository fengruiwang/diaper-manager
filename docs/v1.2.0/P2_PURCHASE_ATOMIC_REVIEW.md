# P2 采购流水和库存必须同事务提交

状态：设计草案，**不得单独在腾讯云执行 008 或 009**。目前无任何生产业务数据被创建/修改。

## 与 v1.1.2 的字段兼容

目前生产程序 \`state.transactions\` 的采购项包含：
\`{id,type:"buy",date,brand,series,size,pieces,price}\`；日常消耗项包含 \`{id,type:"use",date,size,pieces,price:0}\`。

在 v1.2.0 中，对应如下：
- \`operation_id\`：新操作 UUID。旧版短字符串 id 迁移时必须建立稳定映射，不假设旧 id 本身是 UUID。
- \`child_id\`：新增宝宝 UUID；同一家庭可扩展多个宝宝。
- \`purchase_date\`：原有 \`date\` 的日历日期，原样保留，不用服务器提交日覆盖。
- \`brand\`、\`series\`、\`size\`、\`pieces\`：原始采购的商品和数量信息。
- \`total_fen\`：新采购准确到人民币分；客户端负责显式换算，禁止提交非整数分或默默舍入。现有老数据 \`price\` 为 JS number，迁移时如存在超过两位小数，应暂停迁移并核对，不直接截断。
- \`created_by\`：认证 UID，不使用「老婆」等可更改的成员备注。
- \`reversed_by_operation_id\`：撤销该笔采购的反向事件；保留原始流水和原始价格用于审计。

现有未按品牌统计的消耗流水在 \`xb_inventory_operations\` 中按 \`kind=use\` 记录；采购详情在 \`xb_transactions\` 中，与同一 \`operation_id\` 对齐，避免两份互相不匹配的主库存数据。

## 云端提交一体性（下一份 009）

\`xb_apply_inventory_operation\` 新版将添加一个必填参数 \`p_purchase jsonb\`：
- 只有 \`kind='buy'\` 可填写采购数据，且必须包含 brand/series/total_fen/purchase_date 四项。
- 其他 \`use / stocktake / reverse\` 必须传 NULL，禁止把额外购买金额误附在消耗或盘点中。
- 原旧版 9 参数库存 RPC 在替换时会被移除，避免客户端绕过采购详情直接库存 +60。
- 服务器验证权限、操作唯一性、版本与库存边界，在**同一 PostgreSQL 事务**写库存投影、操作事件和采购详情；发生任何错误整体回滚。
- 反向撤销 \`buy\` 时同时设置采购记录的 \`reversed_by_operation_id\`；同一原操作最多撤销一次。撤销后的采购记录仍保留，但活跃累计花费需要排除。
- 服务器计算包括 purchase payload 在内的操作摘要；同一个 ID 改品牌、价格、日期或数量都会被拒绝，不得借重试修改事实。

### 现有旧版行为与新同步的差异（有意更安全）

旧版撤销采购时直接删除历史交易并将库存扣减下限截断为 0（可能静默改变库存），新版必须保留撤销事件。如在本次采购的库存已经消耗后撤销会导致负库存，则提示需要先核对库存，不能静默舍弃部分数量。

旧版累计已花按有效采购记录计算；新版统计要过滤被撤销采购，仍保留可查看的历史和逆向审计。

## 不可越过的门槛

- 不执行 SQL 到 CloudBase 直至 005/007/008/009 的整体部署顺序与权限安全审查完成。
- 用虚拟宝宝、虚拟库存做真实 PostgreSQL 回归：双账号同时购买、超时重试、价格篡改重试、撤销与消耗竞争、权限撤销、跨宝宝/家庭访问。
- 不能将尚未开发的完整购买功能放进正式 v1.1.2 页面，也不能自动导入用户现有 JSON。
- 纸尿裤家用采购目前是 CNY；未来涉及其他币种时必须显式扩展金额和币种，不自动把不同币种相加。
