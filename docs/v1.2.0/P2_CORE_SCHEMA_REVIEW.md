## 第一批业务表及安全界限

1. \`xb_children\`：宝宝独立 UUID、所属家庭、与 v1.1.2 原始单宝宝 \`legacy_slot='primary'\` 的唯一映射。
2. \`xb_baby_profiles\`：独立宝宝的版本化档案，临时 JSONB 容纳尚未正式映射的兼容字段；后续必须增加字段级校验/映射。
3. \`xb_weight_records\`：按宝宝划分的体重数据，保留旧记录 id、测量日期/时间与删除标记，禁止旧记录复活。
4. \`xb_inventory\`：按家庭 + 宝宝 + 尺码的库存投影，有数量与 revision。
5. \`xb_inventory_operations\`：稳定操作 ID、payload_sha256、原库存、新库存、期望修订号、撤销引用和迁移映射。客户端不可直接写入。
6. \`xb_migrations\`：首次历史迁移收据，只有全部导入成功才与初始库存同事务提交；未启用客户端读取。

所有普通客户端只有受 RLS 的 SELECT；不存在直接 INSERT/UPDATE/DELETE 权限。跨家庭用 \`family_id\` 强制隔离；跨宝宝使用复合外键防止交叉绑定。家庭已有账号/成员表不被修改，旧版 localStorage 不被读取或上传。

## 下一步还必须完成，不能把本草案当成正式同步完成

- 库存购买/消耗/盘点/撤销的真实 SECURITY DEFINER RPC：内部验证 auth.uid()/role 和 xb 授权；行锁；检查库存上下限和 revision；在同一事务中写操作事件+库存。
- 重试同一 operation_id / 相同 payload hash 返回原始结果；相同 ID 却不同 payload 必须拒绝，防止库存重复。
- 针对采购流水、候选价格、参考价格、设置、体重编辑 tombstone 的完整表、同步 API 和相应审计。
- 按 \`source_sha256\` 和迁移 ID 幂等执行初次导入；从 v1.1.2 既有采购流水、当前库存与历史体重核对数量，**不能再次把历史采购增量叠加到库存快照**。
- 两台设备各自产生操作，再进行多用户同家庭交叉测试；包括掉线、重放、并发盘点、撤销、删除和跨孩子访问。
- 当前 schema 的旧版事务 ID 唯一性与回滚、追加操作、未来多孩子模型之间必须做假数据并发验收。
- 留待后续版本的喂养/疫苗/提醒业务表**暂不创建**；只承诺 child_id + family_id + actor_uid + revision + deleted_at + outbox 通用合同。
