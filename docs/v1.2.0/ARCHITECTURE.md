# 小宝管家 v1.2.0 — 家庭同步架构（P0 设计基线）

状态：设计 / 独立 Feature 分支；**未发布，未迁移用户数据**。

## 0. 不可突破的兼容约束

- 正式 GitHub Pages \`main\` 继续运行 v1.1.2，直到 P0～P4 全部验收通过。
- 原设备 \`localStorage['xiaobao_diaper_planner_v1']\` 不改键、不删除、不重置；原有 JSON 备份 \`{app:"xiaobao-diapers",version:1,data:{...}}\` 可继续导入。
- 先完成**独立备份和字段/数量核对**，再由用户确认将选定设备的数据初始化到**空家庭**云端；迁移 ID 唯一且幂等，不能重复叠加采购库存。
- 第二台设备如为空，绝对不可上传空快照；如果第二台已有独立记录，则停止自动合并、进入差异审核流程。
- CloudBase 认证与家庭授权必须由云端强制执行，不信任客户端传入的 user_id/role；不得在 PWA 中包含 service_role、SecretKey。
- 任何自动更新不能迫使用户重装 PWA，也不能中断已填写但未保存的表单。

## 1. 共用环境、业务隔离

CloudBase 环境：用户现有 \`xiaobao-family\`（PG 模式、个人版）；GitHub Pages 原域名继续使用。

**共享基础层（可供今后简记使用）**
- \`families\`：家庭 ID、拥有者、创建时间。
- \`family_members\`：家庭成员及角色；仅允许登录用户通过受控 RPC 创建/加入。
- \`family_app_access\`：按家庭、用户、应用授予独立访问许可；\`app_code = 'xb'\` 是小宝管家，\`app_code = 'jj'\` 预留给简记。
- \`family_invites\`：仅通过鉴权 RPC 创建及核销的一次性邀请票据；不允许从网页直接列出或查询票据。

**本轮小宝管家业务层**（P1/P2 分批增加）：
- \`xb_baby_profiles\`、\`xb_weight_records\`：基本资料、历史测量。
- \`xb_inventory\`、\`xb_inventory_operations\`、\`xb_transactions\`：库存投影、服务端事务、购买/消耗/撤销事件。
- \`xb_quotes\`、\`xb_reference_overrides\`、\`xb_settings\`：候选报价、个人参考价、尺码与备货设置。
- \`xb_migrations\`、\`xb_sync_cursors\`：迁移幂等和增量拉取游标。

**明确禁止**：在 v1.2.0 中建 \`jj_*\` 业务表、导入简记账本、让 \`xb\` 成员自动获得 \`jj\` 访问权。

具体的未来扩展与成员备注名兼容方案：见 docs/v1.2.0/EXTENSIBILITY_AND_MEMBER_LABELS.md。P1 成员管理新增 member_alias（显示名）应采用增量迁移，不重建现有已登录成员；P2 建立稳定 child_id，保证后期喂养、疫苗、提醒等功能可独立扩展。

## 2. 身份、授权边界

1. 两人使用各自邮箱验证码登录；匿名身份不能操作家庭数据。
2. **登录 != 加入家庭；加入家庭 != 获得所有应用权限**。仅当 \`family_members\` 与 \`family_app_access\` 均有效时，能读 \`xb\` 数据。
3. PostgreSQL 业务表采用 **GRANT + RLS** 两级访问控制；已登录角色的初始权限应仅为 SELECT（受 RLS 过滤），写入走单一的受控服务端动作。
4. 家庭创建、邀请创建/接受、库存事务等需要 \`SECURITY DEFINER\` 时，函数内部**必须显式验证 \`auth.uid()\` + \`auth.role()\` + 家庭与应用授权**；所有对象 schema-qualified，固定 search_path；禁止依赖前端是否显示按钮。
5. CloudBase 官方 RPC 文档目前提示网关对 EXECUTE GRANT 的强制检查可能不完整：撤销 EXECUTE 是纵深防御，**不能替代函数内身份检查**。
6. 服务器端保留审计事件；删除成员后成员旧 token 不再有家庭读写权限。

参考官方：https://docs.cloudbase.net/database/postgresql/rpc
https://docs.cloudbase.net/authentication-v2/auth/auth-pg
https://docs.cloudbase.net/database/postgresql/data-permission

## 3. 一致性策略（不能上传覆盖整个 state）

| 行为 | 提交模型 | 不能发生的事 |
|---|---|---|
| 采购、消耗 | 客户端创建稳定 \`operation_id\`，服务端在同一事务中去重、记流水、变动库存 | 双人操作互相覆盖；重试重复入库 |
| 库存盘点 | 绝对数量 + \`expected_revision\`，云端锁定行、比对修订号后提交 | 过期盘点覆盖另一人的入库 |
| 撤销购买/消耗 | 新增反向事件并指向原事件；在同一事务验权、校验余额 | 直接删除历史流水导致审计消失 |
| 体重新增/编辑/删除 | 记录 ID 固定、版本校验、删除使用 tombstone | 其他手机无法知道删除；旧体重回写 |
| 宝宝资料、设置、参考价 | 每个实体单独 \`revision\`，乐观并发校验 | 最后上传的整包 JSON 吞掉先前修改 |
| 离线操作 | IndexedDB 持久化操作队列，前台恢复/联网后补传并去重 | 提交结果未知时自动生成新操作 ID |

库存不能仅靠客户端修改 \`state.inventory\` 并上传。服务器是共享库存的最终权威源；本地可暂时预测，但须明确标记“待同步”，同步失败必须保留队列和可恢复原始记录。

## 4. 本地兼容层

**不可撤销的产品要求**：CloudBase 服务停止、套餐到期或网络断开时，本地仍可继续运行、关机重开后恢复缓存，云服务重新开通后重试旧 operation_id 并进行冲突检查。详细故障状态、持久队列要求和双设备补传验收参见 docs/v1.2.0/OFFLINE_RECOVERY.md。正式发布前必须完成该文件全部 P3/P4 验收项；当前基础 outbox 合同测试不代表服务端、浏览器持久化与双手机链路已实现。



- **原键** \`xiaobao_diaper_planner_v1\`：保留完整业务缓存及旧版兼容导入。
- **新独立 IndexedDB**：待同步队列、操作唯一键、云端修订号、上次拉取游标、只读迁移快照。
- 无网络时仍可本地录入，界面显式展示待同步条数；不宣称未确认的操作已到达云端。
- 切换手机、后台恢复、网络重连时触发增量同步；前台活跃时低频定时拉取作为兼容方案（不依赖付费/受邀 Realtime）。
- CloudBase PostgreSQL Realtime 当前官方文档标记 Private Alpha，**本版不可作为生产正确性基础**。

参考：https://docs.cloudbase.net/database/postgresql/realtime

## 5. 数据迁移闸门

阶段 A：原机读取并验证 \`state\`；**不写云端**，展示各尺码库存、采购/消耗/候选报价/体重条数、累计支出，生成加密哈希快照校验值。

阶段 B：用户导出完整 JSON，并主动确认“以当前设备初始化空家庭”；服务端在单事务内核对家庭为空、迁移 ID 未见过，再导入分表/建立初始库存；任一步失败整体回滚。

阶段 C：重复请求同一迁移 ID 只能返回相同结果，不得二次累计库存。验证云端库存、流水条数和参考价后，用户显式启用双向同步。

阶段 D：老婆通过受控邀请码加入，先下载云端数据。已存在的本地独立记录禁止自动清空或自动合并；需先人工核对。

## 6. 阶段验收与发布

- P0：读环境信息、邮箱验证码真实登录、CORS、\`auth.uid()\`、PG RPC、RLS 冒烟测试通过。
- P1：家庭/邀请建表与权限负面测试：未登录、其他家庭、已撤销成员全部拒绝。
- P2：库存原子写入、编辑/删除/并发与幂等测试通过。
- P3：本机队列、完整迁移、旧备份/断网重试恢复通过。
- P4：双手机端到端测试，手动与自动尺码、历史价格和已安装 PWA 原位更新通过。
- P5：只在成功后合入 main，保持缓存与版本号协调发布。任何失败保持 v1.1.2 正式版。

## 7. 约束与非目标

- 不要求用户安装 Node.js 或 CLI；CloudBase 控制台 SQL 编辑器可执行经审阅的迁移 SQL。
- 不在 GitHub 公共仓库上传数据库密码、邮箱、密钥、验证码、家庭邀请码或真实用户导出的备份。
- 本方案适合两名家庭成员，预留未来扩展；不承诺应用关闭后仍持续实时推送。
