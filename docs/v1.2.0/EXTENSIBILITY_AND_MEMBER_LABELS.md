# 小宝管家：可扩展业务模块与家庭成员备注名

状态：v1.2.0 已纳入的架构约束和 P1 功能要求。当前仅为独立开发分支设计，不代表腾讯云线上数据库已增加备注列或主站已经提供修改入口。

## 一、家庭成员：技术身份与显示名称分离

现有 public.family_members 的主键为 (family_id, user_uid)，role 为 owner/member。user_uid 是 CloudBase 认证主体的稳定技术 ID，不应改成备注名，也不能因为重命名而修改采购、体重等操作记录的 actor_uid。

增量扩展（上线前另出安全审查后的迁移脚本，在现有表上 ALTER TABLE 加列，不删除重建）：

- member_alias：家庭内自定义昵称/备注名（例如「我」「老婆」「奶奶」），可空，1–24 个可见字符。
- member_note：可选内部备注（例如「宝宝妈妈」），至多 120 字符。是否启用在 UI 上可后置。
- alias_updated_at：昵称最近修改时间，便于冲突核对。
- 不强制现有两条成员记录填写昵称；旧数据无需重新入群，空昵称展示「管理员」「家庭成员」，不直接显示长 user_uid。
- 页面初始列表以备注名为主、成员角色为副；技术 ID 仅在高级诊断中做脱敏展示。
- 「设置备注」修改的是家庭显示名称，不修改 CloudBase 登录邮箱、权限、家庭关系或审计记录。
- 采购/体重/喂养记录的创建者字段继续存 actor_uid，显示时动态关联 member_alias；改名后历史记录也显示新备注，不更改历史事实。

安全边界：
- 管理员可编辑其家庭所有成员的备注；普通成员只能编辑自己的备注。普通成员不得通过 RPC 更改任意他人的备注、owner 身份、user_uid 或 app_code。
- 前端不可直接 UPDATE family_members；提供单一带身份和家庭归属检查的 SECURITY DEFINER RPC。按现有 CloudBase RPC 网关特性，函数内部必须检查 auth.uid()、auth.role()、目标成员是否属于家庭和 xb 应用授权。
- nickname/notes 经长度和控制字符检查；展示时使用 textContent 或明确 HTML 转义，不将备注当作 HTML。
- 一名家庭成员可以参与未来的简记；共享家庭备注可复用，简记业务表和权限仍然独立。

UI 示意：
  家庭成员
  ┌───────────────────────┐
  │ 我      [管理员]       │  [修改备注]
  │ 老婆    [家庭成员]     │  [修改备注]
  └───────────────────────┘
无需把原始长 ID 作为主要文字。权限管理动作（移除成员等）与备注动作分开，不在本阶段用重命名代替实际权限控制。

验收：
1. 既有家庭 2 人不丢失、不需重新邀请；初始 alias 为空时 UI 有友好退化。
2. 管理员把成员备注修改为「老婆」，双方登录后都能看到。
3. 修改备注不影响 PostgreSQL user_uid、role、family_id 或 xb_app_access。
4. 普通成员改自己的备注允许，修改其他成员或管理员角色拒绝。
5. 角色撤销后不能调用备注 RPC；全程不泄露完整 user_uid 或登录凭证。

## 二、为未来的新功能预留模块结构

未来可能的模块：奶粉/母乳喂养、辅食、疫苗接种计划与实际记录、体检、身高头围、用药提醒、睡眠、宝宝成长里程碑等。v1.2.0 不把这些模块全部开发完成，但数据库和同步框架必须保证以后可增量增加，而不需要替换已在用的本地数据。

设计原则：
- 家庭是访问隔离边界（family_id）；宝宝是业务主体（child_id）；成员是记录创建者（actor_uid）。
- 从 P2 开始确定稳定 child_id：现有单个 babyProfile 第一次迁移时映射为 1 个宝宝实体，生成确定且幂等的 UUID；以后多个宝宝使用不同 child_id。
- 纸尿裤/成长：现有 xb_ 业务表继续使用；至少 baby/profile、weight、diaper 记录需关联 child_id，避免以后引入第二个宝宝时重建全部主键。
- 新增喂养：预留 xb_feeding_records（时间、宝宝、方式、奶量/时长、单位、记录者、备注、revision、删除标记）；只在今后的专门版本建表。
- 新增疫苗：预留 xb_vaccine_catalog / xb_vaccination_records / xb_reminders（地区/来源版本、预计日期、实际接种日、记录者、提醒状态等），规范参考时间表与家庭实际接种事实分离。
- 疫苗计划不可仅靠 AI 推断；需按家长选择的地区、医疗机构建议、可信且更新的官方免疫程序核对；显示「提醒/参考」，不把计划当作医疗记录。
- 通知第一阶段优先 App 内提醒和可查看的待办；浏览器后台推送、电邮推送需额外权限、浏览器和云端计划任务支持，不能保证 PWA 在完全关闭时实时提示。
- 各模块用独立表、独立迁移号、独立权限测试，复用同步操作的稳定 ID / revision / tombstone / outbox 机制，不上传整份 state 覆盖家人记录。
- 新模块可选启用；不影响纸尿裤库存的已有 CRUD 和历史 JSON 格式。未来每个模块新增备份格式版本、迁移和回滚路径。
- 简记沿用家庭基础层，但新的 jj_ 业务表必须独立授权。未来若需要某些成员只能看纸尿裤、不能看疫苗信息，可增设模块级权限，不默认开放所有健康内容。

## 三、v1.2.0 的范围边界

本轮一定做：
- 成员的友好展示名 + 可安全修改的成员备注名；目前 CloudBase 已存在的两名成员使用增量迁移保留原关系。
- 业务实体关联 child_id 和家庭 ID，数据模型、API 和同步结构支持未来模块独立扩展。
- 迁移/同步中保留所有旧字段和未识别新字段，不因为新模块加入就清空老模块。
- 将扩展性写入 P2 schema review / P3 sync / P4 迁移验收。

本轮不做：
- 喂养计时器、奶粉换算、疫苗具体时间表、系统级通知。
- 简记实际云端接入。
- 未经用户确认直接执行 ALTER TABLE、创建新业务表或把真实本地数据迁移云端。
