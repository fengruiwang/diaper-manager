记录日期：2026-11-11。**仅 GitHub Feature 与 GitHub Actions 一次性 PostgreSQL 16；SQL 021/022/023 均不得在真实腾讯云执行。未读取或迁移任何用户真实备份。**

## 本轮核心代码

- `cloudbase/sql/023_xb_legacy_promotion_atomic_DRAFT_DO_NOT_DEPLOY.sql`：在已通过 022 服务端预检并暂存的旧版原始备份上，执行一次数据库事务的正式业务映射原型。
- `tests/postgres/p2_legacy_promotion_atomic_contract.sql`：使用 B1 的两个隔离合成家庭，检查完整升级、重试/权限、库存不重复、错误归档拒绝、收据最后落库，以及**在收据插入时注入错误整笔业务全部回滚**。
- `tests/postgres/p2_legacy_promotion_concurrency.sh`：在同一个临时 PostgreSQL 中启动两个独立连接，尝试同时将同一个归档迁移到同一个宝宝，核验唯一收据和事务级竞态保护。
- 工作流 `.github/workflows/p2-postgres.yml` 已串联 B1 双连接原子归档与 B2 双连接原子提交。所有真实家庭、手机和主分支均无动作。

## 迁移事务的真实步骤

1. 服务端验证 `auth.role()/auth.uid()`、家庭 owner 和 xb 授权，要求仍活跃的 `primary` 宝宝，并获得与 009/022 相同的**家庭级咨询事务锁**。
2. 先检查私有 `xb_migrations` 收据：同一备份的重复响应返回 `ALREADY_PROMOTED_SAME_SOURCE`；更换备份则拒绝；任何迁移结果都**不开放 outbox 上传**。
3. 要求已存在的 B1 完整归档，按服务器重新计算源文本 SHA-256，对照结构化 JSON、三类历史条目的数量、顺序及每条内容；任何不匹配拒绝迁移。
4. 目标所有正式业务表必须为空，不允许对已有库存、历史、宝宝资料或设置做“覆盖式迁移”。
5. 把旧版 `inventory` 六尺码**直接写成绝对库存基线**（包含零库存），修订号均初始化为 1，并各生成一条 `migration_baseline` 审计操作（共六条，`delta=NULL`）；不重放旧采购与消耗。
6. 保存 `xb_baby_profiles` 中的宝宝资料、预产期/生日/体重；写入原生 `xb_weight_records`。原版成长记录（包括空时间）另保留于完整的历史 JSONB 明细，不因原生字段转换而丢失。
7. 新增带家庭 RLS 的 `xb_legacy_history_entries`：逐条保存原样的历史 `transaction/quote/weight` 及原始 ID、顺序和来源校验摘要。它们与 `xb_transactions` 实时采购表隔离，以免触发历史再次入库。
8. 新增 `xb_legacy_settings`：保留目标/日用量、参考价覆盖（0.001 元精度）、补货参数及其他设置；两张新表仅授权同家庭 xb 成员 SELECT，不允许前端直接 INSERT/UPDATE/DELETE。完整不可修改的原始导出仍保存于 B1 私有归档。
9. 在最后写入收据前，**重新核验**六尺码数量和库存总数、基线操作数、各历史记录总数、原生体重数、完整设置与宝宝资料；计算原始历史购买总额（单位分）、买入/使用件数，只写入私有收据计数中，不计入新库存。
10. **最后一个业务写操作**才向 `xb_migrations` 插入不可重复的完成收据。任何阶段出错，包括最后收据 INSERT 被触发器人为阻断，整个数据库调用回滚，原 B1 归档保持完整以便恢复重试。

## 尚未达到正式软件发布条件

- **B2 并不代表旧版历史已可在新 UI 完整编辑。** 旧购买/消耗、报价以专门历史表保存，尚需正式云端分页读取、搜索、明细展示和经过审计的采购修改/撤销/冲正 RPC；不能为编辑直接改写归档。
- **P2-3E 手机持久基线仍未放行。** 真实服务器迁移完成收据只用于证明当时的业务提交；还须核对当前六尺码修订号、另一个设备的 pending 队列、旧版独立备份和账号身份，再原子初始化 IDB。即使收据存在，后续正常库存变化也会让原始备份数量不再等于当前库存。
- 继续进行 CloudBase 真实 SDK 负面权限测试、夫妻两账号互相查询与权限切换、离线重试、采购编辑/冲正、隐私/备份/恢复演练和逐步发布验证。不得因为隔离 CI PASS 就跳过这些。
- 当前已实现的 023 依赖此前尚未安装的 021/022；**不能单独执行 023**。任何真实 SQL、真实历史 JSON 上传和正式生产版本更新，都需要用户单独明确授权。
- 本轮不要求用户再上传测试文件、重跑 SQL 或在正在使用的 v1.1.2 上测试备份导入；未来需要用户测试时，继续在聊天中直接提供每份文件、上传位置、具体步骤、预期结果和脱敏反馈。
