# 小宝管家 v1.2.0 — 已保存采购记录纠错 / 编辑要求

更新：2026-11-11。**正式版必备的新增需求；尚未实现，不代表当前 009 RPC、P2-3B 演练页面或生产 v1.1.2 已支持云端采购编辑。**

## 需求来源与体验要求

用户反馈：“后期录入了购买信息后是否支持修改（担心存在录入错误）？”要求支持在购买记录列表中点击“编辑”，修改品牌、系列、购买日期、支付金额、购买件数与尺码，夫妻双方同步刷新后应得到同一结果，不用让普通用户手动执行撤销/重录两次操作。

客户端应清晰展示“原值 → 新值”，确认提交前预览**对应库存差额、总支出及单片价变化**。必要时提示库存不足、离线待同步或他人已修改冲突，不默默覆盖。

## 现有后端真实能力边界

- 已部署的 `009_xb_purchase_atomic_rpc_draft.sql` 只支持 `buy/use/stocktake/reverse`，不支持 `edit_purchase` 或直接覆盖购买详情。
- `008_xb_transactions_schema_draft.sql` 的 `xb_transactions` 有 `brand/series/pieces/total_fen/purchase_date/size` 字段，但客户端只有 RLS SELECT，**没有 UPDATE 授权**；直接由浏览器 UPDATE 是不允许的。
- 已有 `reverse` 机制不能简单替代所有修改：例如记录已消费一部分、库存不足以反向扣回原购买量时，先完整 reverse 再 buy 会触发负库存保护；**只改价格、品牌和日期也不应该做无意义的库存逆操作**。
- 正式 v1.1.2 手机本地历史数据以及其存储键 `xiaobao_diaper_planner_v1` 均不可受云端编辑功能影响，需单独审查迁移。

## 新增：迁移前旧版历史与迁移后新增采购必须分开纠错（P2-4F 约束）

- 截至 P2-4E-B2 合成隔离验证，旧版购买/消耗历史进入专用 `xb_legacy_history_entries` 原始不可变账本，原始备份归档保留；当前库存六尺码则独立建立绝对基线。`xb_transactions` 保存的才是迁移后的**实时**购入与库存操作。两类采购不允许混用普通 buy/reverse 接口。
- **旧版历史修改品牌、系列、购买日期或支付金额**：应追加不可变的 `legacy_purchase_corrections` 修订事件（候选设计），保留原始 JSON、前/后字段、操作者、审计原因、revision、客户端稳定 `operation_id` 与服务端幂等收据；列表查询展示最新**有效版本**，可查看全部历史。只有字段值变化，不直接改现存库存。
- **旧版历史修改购买件数或尺码**：同样只修正有效历史账本，不自动把过去买的数量再次加入/扣除今天库存。界面必须提示历史账本修正与当前库存盘点为不同操作；若实际库存也不正确，另要求用户确认、重新读取权威库存 revision，再使用受保护的 stocktake RPC。
- **迁移后新采购元数据纠错**：品牌/系列/支付金额/日期更改走审计过的原子编辑接口，库存数量不动。修改数量或尺码时必须在同一事务按**差额**更新受影响尺码库存，任一侧库存不足或 revision 冲突则拒绝并回滚，绝不能重新 `buy` 全量。
- P2-4F-A 已有安全**只读**历史分页与参考价读取草案（SQL 024、SDK 模拟 15 项通过），但还没有实现上述修订表、有效版本合成或真正编辑；**不能把可读当成可改**。
- 权限待决策：家庭中两位具有 `xb` grant 的成员都能读取。编辑默认应由明确授予编辑能力的成员执行，后台保留每一次修改者；不得从 RLS SELECT 自动推导写入许可。
- 正式验收必须覆盖：同一旧历史被两手机同时修改；操作 ACK 丢失后重试；相同操作 ID 不同 payload 被拒绝；撤销修订/修订历史浏览；新采购金额纠错不改库存；历史数量纠错不触碰基线；断网状态不提前显示已同步。不得改写原始迁移档案。

## 原子纠错语义设计（待技术方案审查）

### 1. 纯元数据纠错

- 修改品牌、系列、价格、购买日期：权威采购记录需要更新有效版本，同时追加**不可篡改的前后差异审计记录**，标记修改人、时间、原因/来源与修订号。
- 这类修改不产生新的库存加减，也不改 `xb_inventory.quantity` 和库存 operation receipt；金额汇总与单片价按**最新有效版本**重算。
- 要求操作 ID 幂等与 revision 乐观并发：断网重复提交应只修改一次、不同 payload 使用同一个 ID 必须拒绝。

### 2. 数量/尺码纠错

- 购买数量 60 → 80 且尺码不变时，仅新增**差额 +20** 的权威库存事件，而不是重新累加 80。反向 80 → 60 差额 -20；不能让实际库存负数。
- 购买尺码由 S → M：同一数据库事务对 S 扣回原购买贡献、对 M 增加新贡献，同时修改记录有效版本；任何一侧无法通过非负库存和版本校验，则**整个事务拒绝并回滚**。
- 如果已有使用记录或其他成员同时修改造成库存不足/修订冲突，显示具体差额和冲突，提供由用户确认的库存盘点或分步纠正流程；**不得静默钳制数量、强行改历史、也不得自动改用量**。
- 应与现有 009 采购 RPC 保持相同的 `xb.inventory.family:` 家庭级事务咨询锁键，保证跨账号并发的原子性；新接口不得打破现有 009 的 payload hash/ACK 去重语义。

### 3. 撤销、恢复、历史统计和多设备

- 错误购买完全删除需求：用户界面用“撤销”，后端保留原购买和撤销关联、完整审计。不得直接 DELETE `xb_transactions` / `xb_inventory_operations`。
- 被撤销/被纠错记录在列表中用状态标记并可查看修改历史，支出汇总不重复计入旧版本，库存仅体现最终净变化。
- 夫妻 A/B 在同一家庭具有对应 xb 权限时修改可见；必须定义是否两人都可修改或仅原录入人（产品权限决策待定），每次修改留 actor_uid。
- 真实同步采用已授权云端、客户端持久 IDB outbox、重试与 reconciliation，离线时只显示“待同步修改”，绝不当场标记云端修改成功。
- 修改云端采购记录时绝不自动读取、覆盖或丢弃 v1.1.2 本地历史数据。

## UI 验收样例（未来实现后的必测）

1. A 录入 S 60 片、品牌甲、系列甲、39.99 元；再将品牌/系列/日期/金额改正：数量与库存不变，最新金额正确，审计前后可查看。
2. A 把 60 改为 80：S 库存增加 **20**，两台手机均一致；重复相同 edit operation_id 不再增加 20。
3. A 把 80 改为 50：S 库存减少 **30**；如果当前实际库存不足 30，显示明确错误，事务回滚，不改变原购买记录或库存。
4. A 将 50 片由 S 改为 M：S 减少 50、M 增加 50；任一侧失败时完整回滚。
5. B 修改同一条记录前 A 已改过：B 的旧 revision 必须检测冲突并要求刷新，不可覆盖 A。
6. 同一编辑 operation_id 重放同一 payload：只返回历史 ACK；不同 payload 重用 ID：拒绝。网络故障重试后双方看到同一条当前有效记录。
7. 完全错误的购买被撤销：库存和支出变化正确，审计历史保留；无库存可撤回的异常不允许静默产生负数。
8. 迁移/正式列表必须排除 `legacy_slot` 为 `__xb_smoke_` 前缀的测试宝宝，避免测试采购污染真实统计。
